# Задача завершена только тогда, когда изменение в проде

Прод = ветка `main`. После merge серверы сами разворачивают код за ~5–10 минут
(таймеры `voyn-aicc-worker-release-deploy` на worker-01 и `voyn-aicc-self-deploy` на control-01,
см. `docs/operations/WORKER_RELEASE_DEPLOY.md`). Вручную ничего не деплой и не перезапускай.

## Порядок, когда код готов и локальные проверки зелёные

1. `git fetch origin`. Работай в отдельной ветке от свежего `origin/main` с понятным именем
   (`feat/...`, `fix/...`). Никогда не коммить и не пушь прямо в `main`.
   Не пушь в ветку, у которой PR уже влит или закрыт: проверь `gh pr list --head <ветка> --state all`.
2. В коммите только файлы задачи. Перед пушем пройди ВСЕ локальные проверки из раздела
   «Экономия GitHub» ниже. Пушь только готовый, полностью проверенный результат.
3. `git push -u origin <ветка>`.
4. `gh pr create --base main` с описанием на русском: что сделано, зачем, какие проверки прошли, риски.
5. `gh pr merge <номер> --auto --squash`: GitHub сам вольёт PR, когда пройдут обязательные проверки
   («Final merge gate», «Acceptance gate (independent verdict on exact SHA)»).
6. Жди проверки: `gh pr checks <номер> --watch --interval 60`. Если проверка упала, прочитай лог
   (`gh run view <id> --log-failed | tail -n 200`), исправь в той же ветке, запушь и жди снова.
   Не больше 3 попыток. Потом остановись и опиши, что мешает.
7. После merge убедись, что PR в состоянии MERGED и `origin/main` (после `git fetch`) содержит изменения.
   Сообщи SHA коммита в `main`.
8. Деплой автоматический. Если у тебя нет доступа к серверам, так и напиши:
   «влито в main <sha>, автодеплой ожидается в течение 10 минут, на сервере не проверено».
   Не утверждай, что изменение в проде, без проверки `readlink -f /opt/aicc/current` на сервере.
9. Если менялись `uv.lock`, `pyproject.toml`, `requirements*.txt` или `package*.json`,
   автодеплой откажет (REFUSED: нужен полный installer). Обязательно предупреди об этом в отчёте.

## Экономия GitHub: сначала бесплатно, локально

Репозиторий публичный, поэтому стандартные машины GitHub для него бесплатны, но каждый пуш в PR
запускает CI заново (~8 минут, 12+ задач), занимает очередь merge-gate и стоит агенту полного круга
«ждать → читать лог → чинить». Поэтому GitHub — только финальное подтверждение, а не место для отладки.
Не переводи CI этого публичного репозитория на self-hosted раннеры: чужой PR смог бы выполнить код на наших серверах.

Перед КАЖДЫМ пушем, на этой машине, бесплатно:
1. `make preflight`: пробелы, ruff, компиляция.
2. `make prepush`: preflight плюс тесты, затронутые изменениями, как в CI.
3. Если изменения широкие (общие модули, `conftest.py`, база данных, оркестратор, больше ~5 файлов): `make test-fast`.
4. Если менялось десктоп-приложение: `.venv/bin/python -m pytest tests/desktop -q` (смотри на число passed).
Если хоть что-то красное, исправляй локально и прогоняй заново. Не пушь, пока всё не зелёное.

Правила, чтобы не жечь минуты:
- Один пуш на задачу. Все исправления копи и проверяй локально, потом один пуш.
- Не пушь «посмотреть, что скажет CI», не открывай черновые PR ради проверки.
- Если CI упал, сначала воспроизведи падение локально тем же тестом и почини его; только потом пушь.
- Не перезапускай упавший CI (`gh run rerun`) без изменений, кроме явно сетевых сбоев (таймаут скачивания, недоступен сервис), и не больше 1 раза.
- Не ставь метки `release-gate-canary-*` и другие метки, запускающие дополнительные прогоны.
- Не меняй файлы `.github/workflows/`, если задача не про CI.

## Запрещено всегда, даже ради скорости

- `gh pr merge --admin` и любые обходы обязательных проверок; отключать проверки или защиту веток;
  пропускать и помечать тесты (skip, xfail), чтобы статус стал зелёным.
- `git push --force`, `git reset --hard` по чужим коммитам, пуш прямо в `main`.
- Ручной деплой, перезапуск сервисов через ssh или systemctl, правки на серверах, ручные миграции боевой БД.
- Мержить чужие PR или PR с другими задачами.
