# AML Service — Банковский приёмочный пакет

**Версия:** 1.0
**Дата:** 2026-08-05
**Исполнитель:** Команда разработки AML Service
**Классификация:** Конфиденциально — только для внутреннего использования банка

---

## 1. Аннотация

Настоящий документ является официальным приёмочным пакетом AML Service — программного модуля автоматизированного мониторинга операций, предназначенного для использования кредитными организациями в целях соблюдения требований Федерального закона № 115-ФЗ.

Пакет содержит:
- описание функциональности системы;
- подтверждение соответствия нормативным требованиям;
- процедуры развёртывания и эксплуатации;
- контрольные показатели системы;
- руководство для комплаенс-службы.

## 3. Охват системы

### 3.1 Что система делает

AML Service обеспечивает автоматизированный комплаенс-контроль по следующим направлениям:

**Обнаружение и алертирование**
- Мониторинг финансовых операций на основе настраиваемых правил
- 11 предустановленных правил 115-ФЗ (CTR/STR/PEP/FATF/OFAC)
- Автоматическое создание алертов при срабатывании правил
- Дедупликация алертов по содержательному хешу (SHA-256)

**Управление клиентским риском (CDD/EDD)**
- Ведение клиентских профилей (ФЛ, ЮЛ, ИП)
- Риск-скоринг по факторам: гражданство, отрасль, продукт, PEP-статус, негативные медиа
- Четырёхуровневая шкала риска: low / medium / high / pep
- KYC workflow с отслеживанием сроков обновления

**Движок правил**
- Библиотека типизированных правил с 10 операторами условий
- Поддержка 9 типов алертов (ctr, str, sanctions, pep_related, …)
- Разрезы по юрисдикциям (RU / ALL)
- Полная история срабатываний (`rule_evaluations`)

**Расследование (Case Management)**
- Привязка алертов к делам расследования
- Машина состояний: open → under_investigation → pending_review → closed/escalated_to_sar
- Ролевые ограничения (MLRO/CO): закрытие дела, эскалация в SAR
- Назначение следователей, аудит-лог действий

**Формирование сообщений в регулятор (SAR)**
- Полный жизненный цикл SAR: draft → under_review → approved → submitted → acknowledged
- Автоматический расчёт сроков подачи (STR: 3 дня, CTR: 1 день)
- Регистрация субъектов сообщения
- Отслеживание просроченных SAR

**Compliance Dashboard**
- Составной health score 0–100 (4 пиллара)
- Визуализация трендов алертов (30 дней)
- Нагрузка следователей, статистика SAR по типам
- Перекрёстный мониторинг просрочки по всем модулям

### 3.2 Что система НЕ делает

| Функция | Пояснение |
|---------|-----------|
| Прямая передача данных в ФинЦЕРТ / Росфинмониторинг | SAR формируется в системе; передача — через АРМ банка |
| Электронная подпись документов (ЭЦП) | За рамками данной версии (требует СКЗИ) |
| Интеграция с ГНС/СМЭВ | Внешняя интеграция, не входит в поставку |
| Управление правами доступа пользователей (IAM) | Предполагается интеграция с LDAP/SSO банка |
| Хранение оригиналов документов | Только ссылки на внешние хранилища (`file_ref`) |

## 4. Нормативная база

| Нормативный акт | Применение |
|----------------|-----------|
| Федеральный закон № 115-ФЗ от 07.08.2001 | Основной законодательный фреймворк |
| Ст. 6 — Обязательный контроль (≥ 600 тыс. ₽) | Правила CTR, дедлайн 1 день |
| Ст. 6.1 — CTR ≥ 5 млн ₽ | Правило крупного CTR |
| Ст. 7 — Подозрительные операции | Правила STR, PEP, структурирование |
| Положение Банка России № 375-П | Требования к правилам внутреннего контроля |
| Рекомендации FATF (40 рекомендаций, 2023) | 25 стран Blacklist, типология рисков |
| Список OFAC SDN | 7 санкционных юрисдикций |

## 5. Контрольные показатели (KPI системы)

При приёмочном тестировании на эталонной выборке:

| Показатель | Целевое значение | Примечание |
|-----------|-----------------|-----------|
| Выявление CTR ≥ 600 тыс. ₽ | 100% | Правило обязательного контроля |
| Выявление PEP-признака | 100% | По флагу из клиентской карточки |
| Формирование SAR в срок | 100% | При корректных данных о дедлайне |
| Дедупликация алертов | Нет дублей по одному событию | SHA-256 по source+source_ref |
| Аудиторский след | Полный по всем переходам | Каждое изменение состояния |
| Compliance Health Score | 0–100 (SATISFACTORY ≥ 85) | При чистом портфеле |

## 6. Процедура развёртывания

### 6.1 Требования к среде

| Компонент | Требование |
|-----------|-----------|
| Операционная система | Linux (amd64) / macOS 14+ |
| Docker | ≥ 24.0 |
| Docker Compose | v2 |
| Сеть | Порт 8501 (Streamlit UI) |
| Хранилище | Именованный том Docker (`aml-data`) |

### 6.2 Быстрый старт

```bash
# 1. Получить образ / собрать из исходного кода
docker compose -f docker-compose.aml.yml build

# 2. Запустить сервис
docker compose -f docker-compose.aml.yml up -d

# 3. Проверить доступность
curl http://localhost:8501/_stcore/health
```

После запуска:
- Streamlit UI доступен по адресу `http://localhost:8501`
- Данные хранятся в именованном томе `aml-data` (монтируется в `/data`)
- Правила 115-ФЗ загружаются автоматически при первом старте

### 6.3 Переменные окружения

| Переменная | По умолчанию | Описание |
|-----------|-------------|---------|
| `AICC_DATA_DIR` | `/data` | Директория хранения всех SQLite-баз |
| `STREAMLIT_SERVER_PORT` | `8501` | Порт Streamlit |
| `STREAMLIT_SERVER_ADDRESS` | **нет** | Адрес прослушивания внутри контейнера. Значения по умолчанию нет: без него entrypoint завершается с кодом `78`. `docker-compose.aml.yml` задаёт `0.0.0.0` явно |
| `AML_PORT` | `8501` | Порт публикации на хосте (docker-compose) |

> **Экспозиция.** У сервиса **нет аутентификации**, поэтому порт публикуется только на loopback
> (`127.0.0.1`) — это фиксированное значение в `docker-compose.aml.yml`, а не настройка по
> умолчанию. Переменной для расширения доступа (ранее `AML_BIND_HOST`) больше не существует: четыре
> попытки построить аутентифицирующий прокси перед Streamlit были отклонены на ревью, потому что
> WebSocket-транспорт Streamlit нельзя безопасно проверять на этапе установления соединения (см.
> [ADR-0011](../adr/0011-streamlit-console-no-remote-reachability.md)). Удалённый доступ обеспечивает
> сам оператор сетевыми средствами вне этого сервиса — SSH-туннель или приватный сетевой сегмент до
> порта 8501 на хосте, — а не публикация порта. Публикация порта Docker'ом обходит хостовый firewall,
> поэтому «порт закрыт в firewall» не является защитой.

### 6.4 Резервное копирование

Данные системы хранятся в файлах SQLite в директории `/data`:

```
/data/aml_alerts.db
/data/aml_customers.db
/data/aml_risk.db
/data/aml_rules.db
/data/aml_evidence.db
/data/aml_cases.db
/data/aml_sars.db
```

Резервное копирование — стандартное резервирование тома Docker или файловой системы. Минимальная частота: ежедневно.

## 8. Руководство для комплаенс-офицера

### 8.1 Ежедневные задачи

1. **Проверить Compliance Dashboard** — убедиться, что нет просроченных SAR (`OVERDUE SAR = 0`).
2. **Просмотреть новые алерты** — раздел «AML Monitoring» → «Алерты».
3. **Назначить следователей** — все алерты без назначения должны быть распределены.
4. **Проверить просроченные алерты** — red badge в левом меню.

### 8.2 Работа с CTR (обязательный контроль)

1. Алерт создаётся автоматически при поступлении транзакции ≥ 600 000 ₽.
2. В разделе «SAR» создать CTR: выбрать тип `ctr`.
3. Система автоматически рассчитывает дедлайн (+1 рабочий день).
4. Подготовить нарратив → «На проверку» → MLRO утверждает → «Подать в регулятор».

### 8.3 Работа с STR (подозрительные операции)

1. Алерт создаётся правилом или вручную.
2. Открыть дело расследования → провести расследование → эскалировать в SAR.
3. Создать SAR типа `str` (дедлайн +3 дня).
4. Прикрепить доказательства → согласовать → подать.

### 8.4 Мониторинг просроченных SAR

В Compliance Dashboard → вкладка «SAR» всегда отображается список просроченных SAR с полным описанием. Каждый просроченный SAR снижает health score на 5 баллов.

### 8.5 Роли в системе

| Роль | Возможности |
|------|-----------|
| `Analyst` | Просмотр, создание алертов, проведение расследований |
| `ComplianceOfficer` | Все действия Analyst + закрытие дел, утверждение/подача SAR |
| `MLRO` | Все действия CO + эскалация в SAR |

## 9. Ограничения и замечания

1. **Аутентификация пользователей** — в текущей версии роли передаются параметром `actor` в API. Интеграция с IAM банка выполняется на уровне прокси-сервера или LDAP-шлюза.

2. **Масштабируемость** — система использует SQLite (WAL mode). При объёме > 100 000 алертов/месяц рекомендуется оценить необходимость перехода на PostgreSQL.

3. **Отчётность в Росфинмониторинг** — система генерирует структурированные данные SAR. Форматирование XML-файлов для АРМ банка выполняется отдельным конвертером.

4. **Поддержка** — система поставляется с исходным кодом, полным покрытием тестами и документацией архитектуры.
