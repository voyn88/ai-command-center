# SRV-01b — карта переноса рантайм-стора SQLite → PostgreSQL

Снята машинно 2026-08-13 с обеих живых систем, а не вычитана из исходников:
сторона SQLite — прогоном настоящей `command_center.runtime.db.migrate()` в
одноразовый файл, сторона PostgreSQL — применением настоящей
`command_center/db/sql/0001_initial.up.sql` к одноразовой базе и чтением
`information_schema`. Исходники — это как раз то место, где дрейф прячется.

Карта не поддерживается вручную: её утверждения проверяет
`tests/db/test_schema_correspondence.py` на каждом прогоне CI против настоящего
PostgreSQL. Документ описывает, тест доказывает.

Исключения из этого — два, и оба названы в разделах, где живут: «Объёмы»
ниже записан со слов ранней съёмки и здесь не перепроверяется, а
«Reconciliation» в конце — план сверки, а не выполненная работа. Каждый
помечен так прямо в собственном тексте, а не оставлен читателю на угадывание
по отсутствию ссылки — иначе унаследовал бы достоверность машинных измерений,
которые его окружают.

## Итог сверки

| Величина | Значение |
| --- | --- |
| `SCHEMA_VERSION` SQLite | 23 |
| Доменных таблиц SQLite | **33** (+ служебная `schema_version`) |
| Таблиц PostgreSQL | **33** |
| Соответствие | **1:1, сирот нет ни с одной стороны** |
| Колонок без цели | 0 |
| Различий первичных ключей | 0 |
| Именованных индексов SQLite / PostgreSQL | 62 / 62 |
| Всего индексов PostgreSQL | 102 = 62 именованных + 33 PK + 7 UNIQUE |
| Именованных индексов, потерявших покрытие | 0 (сверка по составу колонок, не по числу) |
| Колонок, меняющих тип / требующих преобразования значений | **114 / 105** из 395 |

Число «16 доменных таблиц» из ранней съёмки **устарело**: оно снято до волн
W1–W3 и занижено более чем вдвое. В расчётах не используется; актуальное
значение закреплено тестом.

## Объёмы: «1.22 млн строк» — экстраполяция, а не измерение

Оценка «≈1.22 млн строк» и производная от неё «бэкфилл ≈6.5 минут» получены
**экстраполяцией с одной таблицы синтетической фикстуры** — файла на ≈35 МБ с
200 000 сообщений и 50 контактов. Продакшн-объём ими не измерен ни разу, и
совпадать с ними он ничем не обязан.

Ранняя съёмка живой базы дала прямо обратную картину: все шестнадцать
доменных таблиц той базы оказались **пусты**, 137 строк на весь файл.
(Шестнадцать — счёт той же устаревшей съёмки, что и в разделе выше; сегодняшняя
схема несёт 33 таблицы. Устарел счёт таблиц, а не наблюдение о пустоте.)

В отличие от разделов выше, снятых машинно, **этот раздел записан со слов той
съёмки и здесь не перепроверяется**: ни живой базы, ни 35-мегабайтной фикстуры
нет ни в репозитории, ни в CI — перемерить число нечем. Раздел обязан читаться
именно так, а не как продолжение измерений вокруг него; поэтому он говорит это
о себе сам, а не оставляет читателю догадываться по отсутствию ссылки.

Следствия, обязательные для SRV-07/SRV-09:

1. Любая цифра объёма в плане переноса несёт при себе слово «экстраполяция» и
   ссылку на источник оценки. Число без пометки читается как измерение —
   именно так эта ошибка и возникла.

2. Окно бэкфилла не планируется по «6.5 минутам»: это тоже экстраполяция, а не
   отдельное измерение, и её ошибка двусторонняя — фикстура, с которой она
   снята, это одна широкая таблица сообщений, чей профиль не похож ни на один
   известный профиль живой базы, так что окно может оказаться и много меньше,
   и много больше.

3. Импортёр измеряет источник сам, на старте: `count(*)` по таблицам в
   порядке волн, до первой вставки, с записью замера в отчёт переноса. Это
   первое настоящее измерение объёма; размер окна выбирается по нему, а не по
   оценке из плана.

4. Пустая исходная таблица — не ошибка импорта и не повод останавливаться, но
   у неё есть обратная сторона: шаг reconciliation «количество строк
   совпадает» (шаг 1 раздела «Reconciliation» ниже) на пустой таблице проходит
   тождественно. Импортёр, не прочитавший ничего, неотличим от импортёра,
   перенёсшего всё, — если измеренный `count(*)` источника не едет в отчёте
   рядом с вердиктом сверки. Зелёная сверка над пустой базой сама по себе не
   доказывает ничего.

Утверждения этого раздела удерживает
`tests/architecture/test_migration_volume_claims_fitness.py`: цифра объёма,
появившаяся в документах переноса без соответствующей пометки, роняет гейт —
как и эта же пара цифр без пометки в любом markdown-файле репозитория. Гейт
сканирует то, что репозиторий сам ведёт (`git ls-files`, не обход диска), а
не чужие `.worktrees/` или локальный `generated/`-отчёт. Проверяется и
способность гейта падать, а не только его зелёный прогон.

## Типы: 114 колонок меняют тип, 105 требуют преобразования значений

Первая редакция этой карты объявляла сверку типов ненужной на том основании,
что объявленные типы SQLite рекомендательны. Это ответ не на тот вопрос.
Опасность не в источнике, а в том, что **цель строже**: PostgreSQL-схема
намеренно взяла продуктовые типы вместо транслитерации, и перенос обязан
конвертировать значения явно.

| Смена типа | Колонок | Нужно ли преобразование значения |
| --- | ---: | --- |
| `TEXT` → `timestamptz` | **75** | да — и это главная опасность, см. ниже |
| `TEXT` → `jsonb` | 22 | да, с проверкой разбора |
| `INTEGER 0/1` → `boolean` | 8 | да, со строгой проверкой 0/1 |
| `INTEGER` → `bigint` | 7 | **нет** (SQLite `INTEGER` уже 64-битный), но все семь — `GENERATED ALWAYS AS IDENTITY`, см. ниже |
| `REAL` → `double precision` | 2 | нет — SQLite `REAL` уже IEEE-754 binary64, значение бит-в-бит то же |
| **Итого** | **114 меняют тип** | **из них 105 требуют преобразования значений** |

**Главная опасность переноса — 75 колонок времени.** `command_center/models.py`
`iso_now()` пишет **наивное локальное время без смещения** и документирует это
прямо: «all timestamps in this app should be read as “local time on the machine
that wrote them”, never assumed to be UTC». Такая строка, загруженная в
`timestamptz`, будет интерпретирована в часовом поясе сессии импортёра: на
UTC-сервере каждая отметка времени молча сдвинется на смещение записавшей
машины, и восстановить исходное значение будет нечем — смещение не хранилось
никогда. Это не теоретический риск, а класс тихой порчи данных, который не
поймает ни один функциональный тест.

**Вторая опасность — семь identity-колонок.** `run_event.id`,
`completion_event.id`, `completion_validation.id`, `proposal_event.id`,
`proposal_evidence.id`, `council_event.id`, `model_event.id` объявлены в
PostgreSQL как `GENERATED ALWAYS AS IDENTITY`. Само значение конвертировать не
надо, но поведение меняется дважды: явный `INSERT` этих `id` **отвергается**
без `OVERRIDING SYSTEM VALUE`, а после переноса последовательность обязана быть
перезапущена за `max(id)` — иначе первая же обычная вставка после миграции
столкнётся с существующим ключом. Это не «расширение типа», это два отдельных
шага импортёра.

Следствия, обязательные для импортёра (SRV-07): часовой пояс источника задаётся
явным решением и фиксируется в отчёте переноса, а не берётся из окружения; JSON
конвертируется с проверкой разбора (нераспознанный текст обязан ронять вставку,
а не молча уезжать в `jsonb`); флаги проверяются на строгое 0/1; identity-колонки
импортируются через `OVERRIDING SYSTEM VALUE`, а их последовательности
перезапускаются после загрузки. Две колонки намеренно остаются `text` —
`owner_item.due` и `digest_item.day` — это свободный пользовательский ввод, а не
даты.

## Nullability

Единственное расхождение nullability, найденное при съёмке, оказалось
артефактом: `PRAGMA table_info` показывает `notnull=0` для собственных колонок
первичного ключа таблицы, хотя ограничение их всё равно требует. Все 32 таких
предупреждения относились ровно к PK-колонкам и ни к чему больше. Поэтому тест
сравнивает состав и порядок PK, но намеренно не сравнивает nullability ключевых
колонок.

## Порядок миграции

Выведен из графа внешних ключей PostgreSQL. Циклов нет, самоссылок нет, значит
порядок вставки, не нарушающий ни одного FK, существует и не требует
отложенных ограничений.

| Волна | Таблицы |
| --- | --- |
| 1 (11) | `advisor_proposal`, `audit_run`, `conflict`, `contact`, `digest_item`, `market_item`, `model_entry`, `motion`, `owner_item`, `queue_entry`, `task` |
| 2 (9) | `audit_finding`, `council_decision`, `council_event`, `council_vote`, `market_install_log`, `message`, `model_event`, `networking_invitation`, `session` |
| 3 (1) | `run` |
| 4 (10) | `completion`, `completion_event`, `completion_validation`, `proposal`, `provenance_evidence`, `provider_attempt`, `report`, `run_event`, `run_provenance`, `run_provider_route` |
| 5 (2) | `proposal_event`, `proposal_evidence` |

Волна 3 — единственная таблица `run`, и это узкое место графа: десять таблиц
четвёртой волны ссылаются на неё. Перенос вертикальными срезами обязан
учитывать, что срез, трогающий `run`, затрагивает почти половину схемы.

## Ограничения (constraints)

PostgreSQL несёт **7 UNIQUE** и **2 CHECK** (`provider_attempt.attempt_number >= 1`,
`run_provider_route.max_attempts >= 1`); в SQLite им соответствуют те же 7 и 2.
Паритет сверяется тестом, а не только заявлен: два CHECK — это предусловия
импорта, и строка источника, их нарушающая, обязана ронять вставку, а не
проходить тихо.

Про индексы: «62 → 102» в первой редакции карты сравнивало разное. SQLite-сторона
считалась по `sqlite_master` без автоиндексов, PostgreSQL-сторона — по
`pg_indexes` со всеми. Честное сравнение — **62 именованных против 62**, а
разница 40 — это 33 PK и 7 UNIQUE автоиндекса. Сверка ведётся по составу
колонок каждого индекса, а не по их числу: равное число при разном составе
означало бы потерю конкретного индекса под горячий запрос.

## Reconciliation (процедура для SRV-07, здесь не исполняется)

Ниже — план сверки, а не выполненная работа: в отличие от разделов выше, эти
шаги ничем в этом PR не проверяются. Выполняются после переноса по каждой
таблице в порядке волн:

1. количество строк совпадает;
2. множество первичных ключей совпадает (а не только их число — равное
   количество при разном составе означает потерю и подмену одновременно);
3. для таблиц с внешними ключами — ни одной висячей ссылки;
4. контрольная выборка значимых колонок сверяется построчно по PK.

Расхождение на любом шаге останавливает перенос: SQLite остаётся authority, и
это состояние обратимо по определению, пока переключение authority не
произошло. Шаг 1 нуждается в оговорке из раздела «Объёмы» выше: на пустой
исходной таблице он проходит тождественно, поэтому измеренный источником
`count(*)` обязан ехать в отчёте рядом с вердиктом — иначе шаг 1 зелёный и на
таблице, из которой ничего не перенесли.

## Ownership

Роли и гранты уже заданы принятой схемой и не пересматриваются этой задачей:
`aicc_migrator` владеет DDL, `aicc_app` — рабочими операциями, `aicc_worker`
ограничен тем, что нужно исполнителю. Перенос не расширяет ничьи права; любое
расширение — отдельное reviewed-решение.
